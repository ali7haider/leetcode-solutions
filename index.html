Computers don't understand JavaScript

Human-readable. Computers can't run this directly.

Something inside the browser must translate your JavaScript into binary so your computer can actually run it. That translator is called the JavaScript Engine.

02 — The Translator

The JavaScript Engine

Every browser ships with one. They all do the same job.

Chrome + Node.js
V8
Built by Google in 2008. Written in C++. Extremely fast. Node.js uses this same engine outside the browser.
Other browsers
SpiderMonkey / JSCore / Chakra
Firefox, Safari, IE each have their own engine. All follow the ECMAScript standard, so they behave the same way.
Node.js insight: Ryan Dahl took Chrome's V8 engine and ran it outside the browser. That is literally how Node.js was created — V8 was already the best engine in existence, so he reused it.

03 — How Engines Translate Code

Interpretation vs Compilation

Interpretation
Line by line
Reads one line, translates it, runs it. Then moves to the next.
Good: stops exactly at an error. Easy to debug.
Bad: slow — constant switching between reading and running.
Compilation
All at once
Translates the entire program first, then runs the output.
Good: much faster execution.
Bad: if there's a bug, you only find it after running — and it can crash the system.
JavaScript used to be purely interpreted (slow). Modern engines use a hybrid called JIT compilation to get the best of both.
4 / 16
04 — The Modern Approach

JIT Compilation — Best of Both Worlds

Just-In-Time. Popularized by Google's V8 engine in 2008.

1
Start by interpreting. The engine interprets your code immediately so it starts running right away. Errors are caught precisely.
2
Watch what actually runs. The engine monitors which functions are used most often — those are the "hot" code paths.
3
Compile the hot parts. Only frequently-used code gets compiled to machine code for maximum speed. Everything else stays interpreted.
Result: fast execution, precise error messages. This is how JavaScript runs today — in both browsers and Node.js.

05 — The Core Concept

What is an Execution Context?

The engine does not run your entire program as one block. It breaks it into smaller pieces and runs each one inside its own isolated environment.

V
Variable Environment
Memory space for all variables and functions declared in this piece of code
S
Scope Chain
A link to the outer environment, so you can access variables defined outside
T
this Binding
Points to the object this code is associated with
Think of an Execution Context like a restaurant table. Each table has its own setup, its own order. But everyone shares the same kitchen (global scope).

06 — The First Context

The Global Execution Context

Created automatically, before a single line of your code runs.

Inside the Global EC from the start
window object — the global object in browsers
this — initially points to window
Variable Object — will hold all your declared variables and functions
Scope Chain — links to outer scopes (initially none, since this is the outermost)
This context is created even if your JavaScript file is completely empty. It is the foundation that every other piece of code runs on top of.
In Node.js, window is replaced by global. The concept is identical.

07 — The Lifecycle

Every EC has 2 Phases

Creation Phase then Execution Phase
Phase 1
Creation
Memory is allocated for all variables
var declarations are set to undefined
Full function bodies are stored in memory
Scope chain and this are set up
No code executes yet.
Phase 2
Execution
Code runs top to bottom, line by line
Variables receive their actual assigned values
Expressions and statements are evaluated
Function calls create brand-new Execution Contexts

08 — Hoisting

Hoisting — the real explanation

You may have heard "variables are moved to the top." That is a simplification. Here is what actually happens.

what you write
greet(); // runs? yes!
console.log(x); // undefined

var x = 5;

function greet() {
  return "Hello";
}
what the engine does
// — Creation Phase —
var x = undefined;
function greet() { ... }

// — Execution Phase —
greet(); // found in memory
console.log(x); // undefined
x = 5; // now assigned
During the Creation Phase, x was already placed in memory with undefined. The function was fully stored. That is why both can be referenced before their written position.

09 — A Critical Difference

var vs let and const

They all declare variables, but their behavior during the Creation Phase is different.

var (ES5 — old)
During Creation Phase, JS sets it to undefined automatically.
You can reference it before the declaration line. You get undefined, not an error.
ES5 design: avoid crashing, use undefined as a safe fallback.
let / const (ES6 — modern)
During Creation Phase, JS allocates memory but keeps them in the Temporal Dead Zone.
You cannot access them before the declaration line. You get a ReferenceError.
ES6 design: be strict, catch bugs early, don't fake initialization.
What is the Temporal Dead Zone?
The period between a variable being created in memory (Creation Phase) and the line where it is actually declared (Execution Phase). During this window, the variable exists but is completely inaccessible. Like a locked phone — it's there, but you can't use it yet.

10 — A New Context Per Call

The Function Execution Context

Every single time a function is called, JavaScript creates a brand-new Execution Context for it.

Global EC
Created once at startup
Contains the window object and this pointing to it
Function EC
Created on every function call
Instead of window, it creates an arguments object — this holds all the values you passed in when calling the function
Everything else is identical — it has its own Variable Object, its own Scope Chain, and its own this. Hoisting works exactly the same way inside a function as it does globally.
When the function finishes, its entire Execution Context — including its Variable Object and Scope Chain — is destroyed. The variables inside it no longer exist.

11 — Keeping Track

The Call Stack

When functions call other functions, multiple Execution Contexts exist simultaneously. JavaScript needs to track all of them.

Call Stack
three()
two()
one()
Global EC
JS Engine
Last In, First Out
1
Script starts. Global EC is placed at the bottom. It never leaves until the program is fully done.
2
one() is called. A new Function EC is pushed on top.
3
two() is called inside one. Pushed on top again.
4
three() is currently at the top — it is the one executing right now.
5
Each function returns. Its EC is popped in reverse order — three, two, one, then Global.
Stack Overflow: too many nested calls — usually caused by a function that calls itself forever (infinite recursion).

12 — Scope

Why Scope works the way it does

Variables only exist inside the Execution Context they were created in.

function hello() {
  var message = "hello world";
}
hello();
console.log(message); // ReferenceError!
1
hello() is called. A Function EC is created. message is added to its Variable Object. The function runs and finishes.
2
When hello() finishes, its EC is destroyed — along with message. The variable no longer exists in memory.
3
The Global EC tries to read message. It is not in global memory. It was never there. The result: ReferenceError.
A child scope can always access its parent. A parent scope can never access its child. This rule comes directly from how Execution Contexts are structured.

13 — Variable Lookup

The Scope Chain

When the engine can't find a variable in the current scope, it climbs outward — one scope at a time — until it finds it or runs out of scopes.

Inner function — three()
d = 4looking for b — not here, checking outer
↓ not found — following scope chain
Outer function — two()
b = 2 — found here
If not found, would check one(), then Global
Global scope
a = 1window
This is called lexical scoping — scope is determined by where code is written, not where it is called from. The chain is established during the Creation Phase.

14 — Closures

How Closures Actually Form

When a function is returned from another function, it keeps a reference to its outer scope — even after the outer function is destroyed.

function doSum(a) {
  return function(b) {
    return a + b; // 'a' lives in closure scope
  };
}
var addTwo = doSum(2); // doSum EC is destroyed here
addTwo(8); // but 'a = 2' is still accessible
1
doSum(2) is called. Its EC is created with a = 2. It returns the inner function. Normally, the EC would be destroyed at this point.
2
But JavaScript detects that the returned function still references a. So it preserves a = 2 in a special Closure Scope instead of erasing it.
3
When addTwo(8) runs later, it looks for a, can't find it locally, follows the scope chain to the Closure Scope, finds a = 2, and returns 2 + 8 = 10.
